{# Decision Flag modal — added 17 Jul 2026 (Decision Flag reply/resolve feature). Shared between dashboard_cs.html ("My Escalated Projects" rows) and dashboard_leadership.html (Decision Needed Queue rows) — both just {% include 'dashboard/_decision_flag_modal.html' %} in the same spot the other dashboard modals live. Same .modal-overlay/.modal-box/.modal-actions shape as _flag_management_modal.html/_reassign_cs_lead_modal.html ("our style"). Unlike those two modals, this one's BODY content is entirely fetched and rendered by JS (openDecisionFlagModal() -> GET /projects//decision- flag, dashboard.js) rather than server-rendered from a Jinja context var — the thread can look completely different between one open and the next (new replies, resolved vs. not), and this modal is triggered from rows on two different dashboards, so there's no single page-load context to render it from ahead of time. Everything below is just the static shell (title, empty containers, buttons) — renderDecisionFlagModal() in dashboard.js rebuilds #decision-flag-original/#decision-flag-thread on every open. Resolve section visibility is driven by the GET response's can_resolve flag (current_user.role in ('admin','management') — see get_decision_ flag() in projects_detail.py), NOT a server-side Jinja gate, since this same shell renders on both dashboards regardless of viewer role — dashboard.js shows/hides #decision-flag-resolve-section after fetching. #}
