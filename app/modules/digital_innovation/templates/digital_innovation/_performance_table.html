{# Performance table — period label, prev/next arrows, the 3 summary stat cards, and the per-project rollup table, all sharing the "view" / "period_key" / "rollup" / "currency" context routes/performance.py's performance_screen() computes once. No separate fragment route for this one (unlike _board_columns.html / _cost_breakdown.html) — Performance has no live-refresh requirement, so switching tabs or periods is just a plain link + the app's existing SPA-nav page swap, not an AJAX fetch. Cost / Charge / Profit per project are LIFETIME totals — identical to what that project's own Cost Breakdown shows, unchanged no matter which period you're viewing. Only Dev Hours (rolled up from THIS period's dev-time entries) and which projects even appear change with the selected period (confirmed with Ezekiel, 2 Sep 2026). The three cards up top are the one place this page shows a period-scoped figure: Total cost = ledger entries dated in this window; Closed / Projected profit = the lifetime profit of every project touching this period, split by whether it's closed or still open. The expanded feature subtable's "Total hours" is that feature's dev hours logged within THIS period (same scoping as the project row's Dev hours column) — "Stage" is just the feature's current status, unrelated to which stage those hours were logged under. Header row added 2 Sep 2026 after Ezekiel flagged the columns reading as if the hours belonged to the stage shown next to them. "di-perf-stats" alongside "di-cost-stats" on the card row below: the Cost Breakdown modal (the other user of .di-cost-stat-card) always has a white .modal-box behind it, but Performance's copy sits straight on the bare page background — .di-cost-stat-card has no border/shadow of its own (just a flat --surface-hover fill), so on the page it barely separates from the page colour in light mode even though it reads fine in dark (see the scoped border in digital_innovation.css). Ezekiel, 2 Sep 2026. #}
